# 实验：长期项目跨对话交接

> 日期：2026-09-19
>
> 执行环境：ChatGPT Project、Codex 桌面端、本地 Git 仓库、GitHub 远端
>
> 结果：通过（限定于连续交接与产物沉淀）

## 研究问题

一个长期 Project 能否让新的执行任务利用先前规划和现有仓库状态，继续产生可审查、可追踪的成果，而不需要用户重新完整描述背景？

## 假设

如果 Project 提供了相关对话上下文，而关键状态保存在 Git 仓库中，那么新任务可以完成“理解目标 → 检查现状 → 实施 → 验证 → 提交”的连续交接。

## 测试材料

- 先前对话中形成的项目定位、四层知识体系和 V0.1 学习路线。
- GitHub 仓库 `xxxx00000008-sketch/ai-workflow-lab`。
- 用户指令：“进行第一阶段”与“完成第一个闭环”。
- 初始化前仅含一个简短 README 的本地仓库。

本记录不包含私人对话全文、凭据或账号敏感信息。

## 步骤

1. 用户引用先前关于项目定位的对话，并要求开始第一阶段。
2. 执行任务读取引用对话的受限预览，提取长期目标、目录设计和 V0.1 顺序。
3. 检查本地仓库，确认只有 README 且工作区干净。
4. 创建知识体系目录、路线图、贡献规范、模板和 Projects 研究入口。
5. 校验相对链接与 Git 差异，在独立分支提交并推送远端。
6. 在新的后续任务中，根据仓库状态和研究入口完成 Projects 知识卡、实验、工作流与案例。

## 原始观察

- 用户没有在新任务中重新粘贴完整规划；引用的前序对话足以恢复目标和阶段顺序。
- 仓库检查补足了对话没有提供的实时事实，避免把规划误当作已完成状态。
- 对话适合传递意图，仓库适合保存最终结构、证据和版本历史。
- 首次实现发现一处错误相对链接和若干尾随空格；本地验证与 Git 检查发现并修复了它们。
- 初始化最终形成 29 个文件和一个独立远端分支，证明交接可以落到可审查产物，而不仅是继续聊天。

## 结果

在本实验范围内，Project 上下文和 Git 状态可以互补：前者恢复目标与理由，后者提供当前事实和可验证产物。交接成功不依赖“模型记住一切”，而依赖任务开始时重新读取权威文件并在结束时回写结果。

## 结论

假设成立，但应收窄为：**Project 能降低长期工作的背景重述成本；要获得可靠连续性，仍需把关键状态外化到可检查文件，并在每次任务中验证当前状态。**

本实验没有证明以下内容：模型总能检索全部历史、不同 memory 模式的行为完全一致、共享 Project 权限正确，或上传文件会自动保持最新。

## 局限与反例

- 本实验只有一个真实项目和一个账号环境，没有做不同订阅方案对照。
- 使用的是用户主动提供的对话引用，不能证明无引用时的历史检索能力。
- 仓库内容由 Codex 直接读取，不能等同于 ChatGPT 对所有项目上传文件的检索表现。
- 未邀请协作者，也未验证 project-only memory 的 UI 设置和隔离效果。
