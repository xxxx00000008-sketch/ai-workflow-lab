# 工作流：ChatGPT Project 生命周期

## 适用场景

- 会持续数天或更久，需要反复返回的研究、写作、规划或开发任务。
- 多次对话需要使用同一套资料、目标和输出标准。
- 希望把对话探索转化为可维护资产。

## 不适用场景

- 无需保留背景的一次性问题。
- 只需要严格文件版本控制、不需要对话协作的机械变更。
- 当前数据政策不允许把相关资料放入 ChatGPT。

## 输入与前置条件

- 一个清晰的长期目标和明确非目标。
- 已确认可放入 Project 的数据范围。
- 一个保存权威状态的位置；软件与文档项目优先使用 Git 仓库。

## 流程

### 1. 初始化

1. 用目标而非工具命名 Project。
2. 写清目标、受众、交付物、质量标准、非目标和隐私边界。
3. 只添加当前必要的资料；为易变化内容标注来源和日期。
4. 建立路线图、任务入口和完成标准。

### 2. 执行单次任务

1. 用一句话声明本次可验收结果。
2. 读取当前权威文件和相关对话，不假设状态仍然有效。
3. 区分官方事实、实验观察与推断。
4. 在独立分支或草稿中产生交付物。
5. 运行与风险相称的验证。

### 3. 沉淀

1. 把最终决策、证据、限制和下一步写入文件。
2. 更新路线图与变更记录。
3. 提交可审查差异；不要把聊天记录当作唯一成果。

### 4. 维护

1. 定期检查重复、冲突和过期资料。
2. 删除不再需要的敏感或临时内容。
3. 当目标、权限或参与者明显变化时，拆分新的 Project。

## 检查点

- 新对话能否仅凭项目说明和仓库文件理解当前阶段？
- 每个结论能否追溯到官方来源或实验？
- 是否存在只在某次对话中、没有写入权威文件的关键决策？
- 项目里是否包含不必要的个人、客户或密钥数据？
- 当前任务是否真的需要 Project，而不是普通对话？

## 输出

- 可复核的交付物和版本历史。
- 更新后的当前状态、决策记录与下一步任务。
- 对适用范围和未验证部分的明确说明。

## 失败处理

- **上下文遗漏**：明确引用权威文件，缩小本次任务范围。
- **资料冲突**：以来源、日期和仓库历史判定，不让模型自行猜测。
- **上下文过载**：归档低价值对话，拆分主题或新建 Project。
- **敏感信息误入**：停止传播，按账号和组织政策删除，并轮换已暴露凭据。
