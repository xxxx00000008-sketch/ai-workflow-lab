# 新成员项目交付操作系统

> 状态：A3 工作流方案；首次完整验证案例为“差价 AI”
>
> 证据等级：E0；目标自动化成熟度：M2
>
> 使用对象：接到一个新客户项目、需要在线协作并交付可运行产品的新成员。

## 怎样使用本页

这不是阅读材料，而是一张执行清单。工具尚未搭建或不清楚分工的新人，必须先阅读 [`新人从零开始交付一个线上项目`](../00-start-here.md)；完成搭建后从步骤 1 开始。每一步必须写清输入、执行动作、输出和确认点。未满足确认点时，处理阻塞而不是跳到开发。

```text
客户问题
  → 确认要交付什么
  → 将确认结果写成可验收契约
  → 做出一条可运行的用户路径
  → 验证、交付、让客户确认
  → 仅沉淀脱敏且可复用的方法
```

## 全局规则

- 企业微信是客户确认的记录渠道；ChatGPT Project 是研究与方案工作区；Git 仓库是工程事实和交付物来源。
- 任何人不得把聊天草稿当作最终需求。最终范围必须进入交付契约。
- 任何 AI 生成的数据、代码或结论都必须按风险接受人工核验。
- 没有客户可验证的结果，就不称为“已完成”。
- `ai-workflow-lab` 只保存目录、模板、流程规则和脱敏经验，不保存客户原始资料、源代码、密钥或验收记录。
- 未获得客户文字确认的交付契约前，执行者只能做只读调查和方案草稿；不得开始编码、提交、推送、部署或称为“已交付”。

## 步骤 1：启动与授权

**第一步具体做什么：** 在企业微信建立项目群或已有群内的固定沟通线程，发送项目启动摘要，确认谁提需求、谁验收、谁拥有仓库与发布权限。

| 输入 | 具体动作 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 客户目标、上线时间、已有材料 | 询问核心用户、核心任务、期限、技术限制、现有 Demo/仓库/域名；列出缺失权限 | 项目摘要、联系人角色表、权限清单、风险清单 | 有唯一验收人；知道仓库和预览/生产环境如何访问 |

**客户消息模板：** “为保证按期交付，请确认：本项目唯一验收人是谁；首期要让哪类用户完成什么任务；本周必须交付什么；哪些功能明确不做；仓库和发布权限由谁提供。”

若没有验收人或发布路径，交付目标应改为“可运行仓库”，不能承诺上线。

## 步骤 2：确认用户问题与 MVP 范围

| 输入 | 具体动作 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 客户描述、竞品、Demo、目标用户 | 将“想做的网站”改写成一条用户任务；列出必要功能、可延期功能和明确不做项；只保留能在期限内完成的一个核心路径 | 用户任务、MVP 范围表、非目标清单、成功指标 | 客户以文字确认核心任务和非目标 |

正确写法是：“中国用户可以搜索一个 AI 产品，比较其套餐、地区价格和可用性，并看到来源与更新时间。”

错误写法是：“做一个类似某竞品的完整网站。”后者无法验收，也会导致不断加功能。

## 步骤 3：创建交付契约

在仓库 `docs/delivery-contracts/` 中建立唯一编号，例如 `DELIVERY-CHAJIA-001`。至少包含：

1. 用户问题和验收人；
2. 本次范围与非范围；
3. 页面/API 的可观察行为；
4. 数据来源、更新时间和异常表现；
5. 三到五个客户可操作的验收示例；
6. 测试、发布、回滚和已知限制；
7. 批准日期和批准记录链接或编号。

将草稿在企业微信确认，批准版本提交 Git。需求改变时创建新版本，不悄悄修改已批准范围。

## 步骤 4：设计首个可运行垂直切片

| 输入 | 具体动作 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 批准契约、现有代码、数据样本 | 画出一条用户从进入页面到获得结果的完整路径；确定最少页面、数据、接口、错误状态和测试 | 线框或原型、数据契约、开发任务列表 | 每个任务都能关联到契约的一个验收示例 |

例如差价 AI 的第一条切片不是“做完所有 AI 产品”，而是“搜索一个产品 → 查看有限地区与套餐 → 理解人民币估算、来源和更新时间 → 看见无数据时的解释”。

## 步骤 5：实现与每日线上协作

每天按以下固定节奏执行：

1. **开始前**：读取交付契约、`AGENTS.md`、现有代码和测试；确认今天只完成哪个验收示例。
2. **实现中**：在独立分支或 worktree 修改；小步提交；不要把密钥、客户数据或临时绕过方案提交到仓库。
3. **当天结束前**：部署到预览环境，自己走完核心路径；运行测试；在企业微信说明“已完成、可演示链接、明日计划、阻塞项”。
4. **客户反馈后**：把反馈分为缺陷、澄清或新范围。只有缺陷直接进入当前迭代；新范围回到步骤 3。

ChatGPT Project 用于整理研究与决策，Codex 用于检查与修改真实仓库。两者的内容不会自动同步，批准的契约和 Git 提交才是交接依据。

## 步骤 6：测试与客户验收

开发者先完成以下最小检查：

- 主用户路径和关键错误路径可以运行；
- 数据来源、日期、价格/文案等高影响信息已人工核对；
- 移动端基础布局、主要链接、加载与空状态可理解；
- 自动化测试、构建和代码检查通过；
- 环境变量只记录名称；仓库无密钥、令牌和个人数据；
- 有明确的回滚或恢复步骤。

随后让客户按交付契约中的验收示例操作真实预览版本。验收意见要写成“哪个步骤、预期什么、实际什么”，而不是“感觉不对”。

## 步骤 7：发布或仓库交付

客户验收通过后，交付至少包括：可运行仓库、`README`、启动方式、环境变量名称清单、部署说明、回滚方式、已知限制和下一步建议。

若具备发布授权，则发布后立即做一次冒烟测试：首页、核心路径、数据加载、登录/权限（如有）与错误监控。发布失败按回滚方案恢复，通知客户事实与恢复时间，不隐瞒问题。

## 步骤 8：复盘并改善 ai-workflow-lab

复盘只回答四个问题：

1. 新成员在哪一步最容易停住？
2. 哪个模板字段缺失，导致返工或误解？
3. 哪个质量门禁最有效，或最不必要？
4. 下次怎样让交付更快、更可靠且风险更低？

将答案脱敏后更新本知识库的工作流、模板或目录说明。不要复制客户交付记录；通过改进“下一位新人第一步要做什么”来实现复用。

## 项目仓库标准目录

```text
project/
├── AGENTS.md                         # 本仓库的开发、测试与安全规则
├── README.md                          # 启动、运行与交付说明
├── docs/
│   ├── delivery-contracts/            # 已批准范围与验收标准
│   ├── decisions/                     # 关键取舍及原因
│   ├── data/                          # 数据来源、字段与更新规则
│   └── operations/                    # 部署、回滚、监控与故障处理
├── src/                               # 产品实现
├── tests/                             # 单元、集成和端到端测试
├── scripts/                           # 可审查的维护脚本
├── deployment/                        # 部署配置和说明
└── .github/                           # CI、审查与发布门禁
```

这是结构建议，不是空目录创建任务。先用真实项目的技术栈和现有结构审查后再决定是否采用。

## 完成定义

一个项目完成，必须同时满足：客户能按验收示例完成核心任务；授权方能按文档运行或部署；限制与风险透明；客户留下明确验收确认；可复用流程已脱敏更新到 `ai-workflow-lab`。
