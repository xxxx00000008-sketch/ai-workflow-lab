# 新成员项目交付操作系统

> 状态：A3 工作流方案；首次完整验证案例为“差价 AI”
>
> 证据等级：E0；目标自动化成熟度：M2
>
> 使用对象：接到一个新客户项目、需要在线协作并交付可运行产品的新成员。

## 怎样使用本页

这不是阅读材料，而是一张执行清单。工具尚未搭建或不清楚分工的新人，必须先阅读 [`新人从零开始交付一个线上项目`](../00-start-here.md)；完成搭建后从步骤 1 开始。每一步必须写清输入、执行动作、输出和确认点。未满足确认点时，处理阻塞而不是跳到开发。

```text
客户问题
  → 确认要交付什么
  → 将确认结果写成可验收契约
  → OpenSpec 定义包 → 方案包 → 实现与验收
  → 按任务做出一条可运行的用户路径
  → 验证、交付、让客户确认
  → 仅沉淀脱敏且可复用的方法
```

## 全局规则

- 企业微信是客户确认的记录渠道；ChatGPT Project 是研究与方案工作区；Git 仓库是工程事实和交付物来源。
- 任何人不得把聊天草稿当作最终需求。最终范围必须进入交付契约。
- 任何 AI 生成的数据、代码或结论都必须按风险接受人工核验。
- 没有客户可验证的结果，就不称为“已完成”。
- `ai-workflow-lab` 只保存目录、模板、流程规则和脱敏经验，不保存客户原始资料、源代码、密钥或验收记录。
- 未获得客户文字确认的交付契约前，执行者只能做只读调查和方案草稿；不得开始编码、提交、推送、部署或称为“已交付”。

## 步骤 1：启动与授权

**第一步具体做什么：** 在企业微信建立项目群或已有群内的固定沟通线程，发送项目启动摘要，确认谁提需求、谁验收、谁拥有仓库与发布权限。

| 输入 | 具体动作 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 客户目标、上线时间、已有材料 | 询问核心用户、核心任务、期限、技术限制、现有 Demo/仓库/域名；列出缺失权限 | 项目摘要、联系人角色表、权限清单、风险清单 | 有唯一验收人；知道仓库和预览/生产环境如何访问 |

**客户消息模板：** “为保证按期交付，请确认：本项目唯一验收人是谁；首期要让哪类用户完成什么任务；本周必须交付什么；哪些功能明确不做；仓库和发布权限由谁提供。”

若没有验收人或发布路径，交付目标应改为“可运行仓库”，不能承诺上线。

## 步骤 2：确认用户问题与 MVP 范围

| 输入 | 具体动作 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 客户描述、竞品、Demo、目标用户 | 将“想做的网站”改写成一条用户任务；列出必要功能、可延期功能和明确不做项；只保留能在期限内完成的一个核心路径 | 用户任务、MVP 范围表、非目标清单、成功指标 | 客户以文字确认核心任务和非目标 |

正确写法是：“中国用户可以搜索一个 AI 产品，比较其套餐、地区价格和可用性，并看到来源与更新时间。”

错误写法是：“做一个类似某竞品的完整网站。”后者无法验收，也会导致不断加功能。

### 动手前必须画出核心链路

页面不是核心链路。AI 必须继续询问并得到客户确认：

```text
触发者/触发条件
→ 输入或数据来源
→ 核心处理与决策
→ 状态变化
→ 用户可见结果
→ 失败表现与恢复
→ 离场后的持续运行者
```

对于动态系统，必须额外确认更新频率、自动与人工边界、外部依赖失败行为和新鲜度；对于交易系统必须确认权限、幂等和资金状态；对于内容系统必须确认创作、审核和发布责任。通用流程只强制问题完整，不预设答案。

## 步骤 3：创建交付契约

在仓库 `docs/delivery-contracts/` 中建立唯一编号，例如 `DELIVERY-CHAJIA-001`。至少包含：

1. 用户问题和验收人；
2. 本次范围与非范围；
3. 页面/API 的可观察行为；
4. 数据来源、更新时间和异常表现；
5. 三到五个客户可操作的验收示例；
6. 测试、发布、回滚和已知限制；
7. 批准日期和批准记录链接或编号。
8. 核心正常链路、失败链路和恢复原则；
9. 自动化边界、离场运行方式和持续变化数据的责任；
10. 用户可感知的性能、可用性、容量或新鲜度目标；没有基线时写明待测。

将草稿在企业微信确认，批准版本提交 Git。需求改变时创建新版本，不悄悄修改已批准范围。

## 步骤 4：完成 OpenSpec 定义包和方案包

| 输入 | 具体动作 | 输出 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 批准契约、现有代码、数据样本 | 先建立一个聚焦的 change proposal；按 capability 生成并确认无实现细节的需求 spec；再生成技术 plan/design；最后拆成可独立验证的 tasks，并选出首条完整用户路径 | 已确认 proposal/spec、技术方案、原子任务列表、线框或目标 Demo、数据契约 | proposal 范围聚焦；spec 与契约一致；plan 通过原则检查；每个任务能关联需求编号和验收场景 |

详细方法见 [`OpenSpec 三阶段交付法`](spec-plan-tasks-compilation.md)。`proposal + specs` 一次通过需求门禁，`design + tasks` 一次通过实施门禁；不逐文件审批。

Design 是技术架构方案，不是需求复述。新项目没有既有技术栈时，必须先比较候选方案，再确定语言、框架、运行时、数据、异步任务、部署和测试选型。所有项目都必须说明关键链路、异常恢复、数据所有权、安全、可观察性、性能、容量、可扩展边界和首个垂直切片；这些内容缺失时不得生成 tasks。

例如差价 AI 的第一条切片不是“做完所有 AI 产品”，而是“搜索一个产品 → 查看有限地区与套餐 → 理解人民币估算、来源和更新时间 → 看见无数据时的解释”。

### 已有 Demo 的例外路径

如果客户明确确认现有 demo 就是本期要实现的目标 demo，可以跳过“从零制作原型”。仍必须：审查该 demo 的实际页面与用户路径、把保留和变更项写入交付契约、确认数据和验收标准，并按后续实现与验收门禁推进。没有客户明确确认时，旧 demo 只能作为研究输入，不能替代目标 demo。

如果产品包含公开或视觉型界面，且现有 demo 没有被明确确认是目标成品，必须先制作独立的原创 UI 原型并取得明确确认，再进入运行时、数据和部署实现；参考站只能作为信息结构和验收输入。

目标 Demo 只决定用户看见什么、怎样操作和如何验收，不决定语言、框架、数据库、托管或扩展架构。只有在客户明确要求接管一个已有生产系统，且仓库与运行证据证明其技术正在使用时，现有技术栈才属于 Design 约束。

Design 与 tasks 必须同时给出环境能力矩阵、端口/适配器替换边界，并把测试环境证据与生产上线证据分开记录；本地替代实现只能证明业务契约，不得证明目标平台能力。

数据库或状态系统不能只设计“表结构”。Design 必须区分三类初始数据：系统运行必需的目录/配置、只能由自动流程产生的业务事实、禁止进入仓库的密钥或客户数据。部署任务要验证配置键与运行时代码实际读取的名称一致、迁移工具能定位迁移目录、空环境能够生成最小可运行目录，并确认业务事实仍为空；否则“迁移成功”不等于“系统可启动”。

可扩展性不能只写“以后方便新增”。产品、来源、地区、币种或租户等会持续增长的目录必须确定唯一配置源，所有种子、API、页面、索引或导航从同一配置派生；再用一个虚拟条目做扩展契约测试，证明新增条目不需要给调度、校验、比价或查询主链路增加厂商分支。

## 步骤 5：实现与每日线上协作

每天按以下固定节奏执行：

1. **开始前**：读取交付契约、当前 OpenSpec change 中已批准的 proposal、specs、design、tasks，以及 `AGENTS.md`、现有代码和测试；确认今天只执行哪个原子任务及其验收场景。
2. **实现中**：在独立分支或 worktree 修改；小步提交；不要把密钥、客户数据或临时绕过方案提交到仓库。
3. **当天结束前**：部署到预览环境，自己走完核心路径；运行测试；在企业微信说明“已完成、可演示链接、明日计划、阻塞项”。
4. **客户反馈后**：把反馈分为缺陷、澄清或新范围。只有缺陷直接进入当前迭代；新范围回到步骤 3。

ChatGPT Project 用于整理研究与决策，Codex 用于检查与修改真实仓库。两者的内容不会自动同步，批准的契约和 Git 提交才是交接依据。

### 多代理或多人并行写入规则

- 每个写任务使用独立分支或 worktree，并登记负责人、允许修改的模块和验收输出。
- 共享清单、锁文件、数据库迁移、公共类型和部署配置默认只由集成负责人修改；确需并行时先约定所有权。
- 执行者结束时必须报告实际改动文件、运行过的验证、未完成项和工作区状态，不得自行勾选总任务清单。
- 集成负责人重新读取合并后的工作区并运行组合验证，确认接口、迁移和生成物没有冲突后，才更新总任务状态。
- 安全和编码测试必须改变解码后的真实语义或字节，不得只改 Base64、压缩、序列化等表示层的末尾字符；否则未使用填充位可能让“伪造数据”与原数据相同，形成偶发通过。

## 步骤 6：测试与客户验收

开发者先完成以下最小检查：

- 主用户路径和关键错误路径可以运行；
- 数据来源、日期、价格/文案等高影响信息已人工核对；
- 移动端基础布局、主要链接、加载与空状态可理解；
- 自动化测试、构建和代码检查通过；
- 构建后仓库状态已复核：临时包、哈希产物、报告和缓存要么被忽略，要么是明确交付物；不得把本机构建噪声混入提交；
- 环境变量只记录名称；仓库无密钥、令牌和个人数据；
- 有明确的回滚或恢复步骤。

证据必须标明覆盖层级。单元/契约测试可以使用替身，但不能据此声称真实数据库、队列、定时任务、部署平台或公开入口已经验证。核心链路至少保留一次从真实或目标兼容存储经过 API 到用户入口的验证；目标平台能力未验证时明确写“未验证/阻塞”。

若系统包含持续变化的数据、后台任务或外部集成，交付前还要完成一次自动执行、一次授权手动触发，并演练超时、重复、非法输入、外部依赖失败、保留最后正确状态、告警和恢复。最好由非实现者按运行手册完成一次操作。

随后让客户按交付契约中的验收示例操作真实预览版本。验收意见要写成“哪个步骤、预期什么、实际什么”，而不是“感觉不对”。

## 步骤 7：发布或仓库交付

客户验收通过后，交付至少包括：可运行仓库、`README`、启动方式、环境变量名称清单、部署说明、回滚方式、已知限制和下一步建议。

若具备发布授权，则发布后立即做一次冒烟测试：首页、核心路径、数据加载、登录/权限（如有）与错误监控。发布失败按回滚方案恢复，通知客户事实与恢复时间，不隐瞒问题。

交付前执行一次干净环境复现：从新检出开始，严格按 README 完成依赖安装、配置检查、迁移/初始化、构建、启动和最小用户路径。记录不能自动提供的外部资源、负责人和当前状态；最好由未参与实现的人执行。作者机器可以运行不等于仓库可交付。

运行手册必须写到可操作级别：角色和禁止事项、资源创建、配置检查、迁移与初始数据、首位操作员或系统身份建立、部署顺序、自动与手动触发、指标与告警、失败恢复、回滚和扩展方式。首次初始化不得依赖 FDE 记忆中的隐藏步骤；如果必须通过平台控制台完成，要写明负责人、入口、输入、验收结果和不可自动化原因。

## 步骤 8：复盘并改善 ai-workflow-lab

复盘只回答四个问题：

1. 新成员在哪一步最容易停住？
2. 哪个模板字段缺失，导致返工或误解？
3. 哪个质量门禁最有效，或最不必要？
4. 下次怎样让交付更快、更可靠且风险更低？

将答案脱敏后更新本知识库的工作流、模板或目录说明。不要复制客户交付记录；通过改进“下一位新人第一步要做什么”来实现复用。

## 项目仓库标准目录

```text
project/
├── AGENTS.md                         # 本仓库的开发、测试与安全规则
├── README.md                          # 启动、运行与交付说明
├── openspec/
│   ├── specs/                         # 当前已经交付并验证的系统行为
│   │   └── capability/spec.md
│   └── changes/
│       └── change-id/
│           ├── proposal.md            # 为什么改、改什么
│           ├── specs/capability/spec.md # ADDED/MODIFIED/REMOVED 行为
│           ├── design.md              # 技术方案；现有项目可命名为 plan.md
│           └── tasks.md               # 可执行、可验证的原子任务
├── docs/
│   ├── delivery-contracts/            # 已批准范围与验收标准
│   ├── decisions/                     # 关键取舍及原因
│   ├── data/                          # 数据来源、字段与更新规则
│   └── operations/                    # 部署、回滚、监控与故障处理
├── src/                               # 产品实现
├── tests/                             # 单元、集成和端到端测试
├── scripts/                           # 可审查的维护脚本
├── deployment/                        # 部署配置和说明
└── .github/                           # CI、审查与发布门禁
```

这是结构建议，不是空目录创建任务。先用真实项目的技术栈和现有结构审查后再决定是否采用。

## 完成定义

一个项目完成，必须同时满足：客户能按验收示例完成核心任务；授权方能按文档运行或部署；限制与风险透明；客户留下明确验收确认；可复用流程已脱敏更新到 `ai-workflow-lab`。
