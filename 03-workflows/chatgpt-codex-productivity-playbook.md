# ChatGPT + Codex 实际工作提效手册

> 最近验证：2026-09-19
>
> 适用对象：知识工作者、内容创作者、独立开发者和小团队

这份手册不按功能按钮教学，而是把工作分成“传统做法、AI 协作做法、自动化做法”三个层级。先让一次任务稳定成功，再考虑重复和自动化。

## 一、先建立四级工作模型

| 级别 | 工作方式 | 人负责什么 | AI 负责什么 |
| --- | --- | --- | --- |
| L0 传统 | 全程手工 | 搜集、整理、执行、检查 | 不参与 |
| L1 对话辅助 | Chat 提供建议 | 提供材料、复制执行、判断 | 解释、改写、头脑风暴 |
| L2 任务交付 | Work 或 Codex 完成成果 | 定义结果、授权、审查 | 读取来源、使用工具、产生文件、验证 |
| L3 标准化 | Project、AGENTS.md、Skill | 维护规则和模板 | 按稳定流程重复执行 |
| L4 自动化 | Scheduled、Automation、插件 | 处理异常和最终审批 | 定时获取、处理、检查并通知 |

效率提升最大的变化不是“提示词写得更长”，而是从 L1 的问答升级到 L2 的成果交付，再把稳定过程升级到 L3/L4。

## 二、推荐主架构：ChatGPT Project + Codex Project

对于长期写作、研究、知识库和独立开发，最实用的不是在 ChatGPT 与 Codex 之间二选一，而是让它们承担不同责任。

```text
ChatGPT Project
目标、读者、研究资料、讨论、写作决策
          ↓ 已确认的结构与内容
本地 Git 仓库
文章、素材、模板、实验、状态、版本历史
          ↑ 读取与写入
Codex Project
批量编辑、链接检查、文件生成、Diff、提交、自动化
```

### ChatGPT Project 负责“想清楚”

- 保存长期定位、目标受众和写作风格。
- 集中官方资料、访谈、参考文件和相关对话。
- 进行选题、提纲、论证、反方检查和改写讨论。
- 使用 Search/Deep Research 获取最新信息。
- 使用 Work 制作报告、演示、表格和长文草稿。

### Codex Project 负责“落到真实文件”

- 读取本地知识库或代码仓库。
- 按目录规范创建和修改多个文件。
- 查找重复内容、坏链接、过期日期和遗漏索引。
- 运行验证、查看 Diff、形成 Commit 和 PR。
- 把稳定规则放入 `AGENTS.md`，把重复流程变成 Skill 或 Automation。

### Git 仓库负责“成为事实”

ChatGPT 对话中的内容仍是讨论；进入仓库并经过 Diff 审查、验证和提交后，才成为项目的正式资产。不要把唯一版本的文章、决策或实验结果只留在对话中。

### 一次标准交接

ChatGPT Project 输出给 Codex 的不是整段聊天，而是一份明确任务：

```text
已确认选题：Codex worktree 如何支持并行工作。
目标读者：第一次使用 Codex 的独立开发者。
核心结论：worktree 用于隔离并行写入，不等于新的远端仓库。
官方来源：[链接]
文章结构：[五个章节]
需要 Codex 完成：写入指定目录、更新索引、检查链接、提交分支。
不得做：补写未经验证的账号限制、直接合并 main。
```

Codex 完成后，把文件路径、Diff、验证结果和未决问题返回 ChatGPT Project，继续做内容判断或下一轮写作。

## 三、产品功能怎样映射到工作

| 工作需要 | 使用功能 | 实际作用 |
| --- | --- | --- |
| 临时讨论和快速判断 | Chat | 降低思考和表达成本 |
| 长期共享背景 | Project | 集中对话、文件和指令 |
| 最新公开资料 | Search / Deep Research | 获取带来源的当前信息 |
| 多步骤成品 | Work | 制作文档、表格、演示和报告 |
| 本地仓库和文件 | Codex | 读取、修改、运行、验证和提交 |
| 稳定团队规则 | Project instructions / `AGENTS.md` | 避免每次重复说明 |
| 重复方法 | Skill | 封装步骤、模板和检查标准 |
| 外部系统 | Plugin / MCP | 读取和操作 Slack、Drive、GitHub 等 |
| 周期工作 | Scheduled / Automation | 定时运行、监控和通知 |
| 并行开发 | Codex Thread + worktree | 隔离多个 Agent 的写入 |
| 结果把关 | Diff / Review / Preview | 人工确认实际变化和风险 |

官方用例同样将产品能力组织为研究、知识工作、工程、质量和自动化工作流，而不是孤立按钮。[OpenAI use cases](https://learn.chatgpt.com/use-cases?category=automation&category=engineering&category=sciences&task_type=analysis&task_type=code&task_type=testing&team=design-engineering&team=education&team=operations&team=product)

## 四、场景一：从资料搜集到决策报告

### 传统做法

```text
搜索关键词
→ 打开十几个网页
→ 复制内容到笔记
→ 手工去重和比较
→ 写报告
→ 补来源
→ 修改格式
```

问题：时间主要消耗在搬运信息；来源和判断容易混在一起；更新一次几乎要重做。

### ChatGPT 协作做法

1. 在 Project 中保存目标、受众和长期资料。
2. 使用 Search 或 Deep Research 搜索最新公开来源。
3. 要求先输出证据表，再形成建议。
4. 使用 Work 生成决策备忘录或演示文稿。
5. 人工核查关键来源、数字和反对意见。

可直接使用的任务：

```text
目标：比较三种适合个人知识库的 AI 工作方式，并给出选择建议。
时间范围：只使用 2026 年仍有效的资料。
来源：优先官方文档和产品公告；打开原文，不使用搜索摘要作为证据。
输出：
1. 一页结论；
2. 证据对照表；
3. 成本、风险和不确定项；
4. 推荐方案及不推荐方案。
把来源事实、你的推断和我的偏好分开标注。先返回提纲，确认后再写完整报告。
```

### 自动化做法

当问题变成每周重复监测时：

```text
每周一检查指定官方来源的更新。
只报告会影响现有决策的变化：功能下线、价格变化、权限变化或新限制。
无实质变化时保持安静。
发现变化时输出：原结论、最新证据、影响、建议动作。
不要自动修改正式报告，等待我批准。
```

### 人工检查点

- 引用是否真的支持结论。
- 信息发生日期是否与发布日期一致。
- 建议是否混入未经声明的价值判断。
- 自动化是否只监测已批准来源。

## 五、场景二：从会议记录到执行跟进

### 传统做法

开会后人工整理纪要、识别负责人、逐个创建任务、发送跟进并在下次会议前重新汇总。

### ChatGPT Work 做法

输入：会议录音转写、议程、项目文档和相关消息。

```text
根据会议记录生成执行纪要。
只提取明确发生的决策、行动项、负责人、截止时间和未决问题。
不要为没有负责人的任务猜测负责人。
把“原话证据”和“整理后的行动”分栏展示。
先给我审查；不要发送消息或创建外部任务。
```

输出：

- 决策清单。
- 行动项表格。
- 无负责人的待确认事项。
- 可供人工发送的跟进消息草稿。

### 插件与自动化做法

在团队批准连接 Zoom、Slack、Calendar 和任务系统后：

1. Scheduled 在会议后触发。
2. 插件读取批准的会议内容。
3. Work 生成纪要和任务草稿。
4. 人工确认负责人、日期和措辞。
5. 批准后再写入任务系统或发送消息。

自动化的目标不是取消审批，而是让人只处理含糊项和最终发送。

## 六、场景三：从需求到代码交付

### 传统做法

开发者阅读需求、搜索代码、手工修改、切换终端运行测试、检查 Git、写提交、开 PR，再手工回复审查意见。

### Codex 协作做法

1. 在正确仓库开启独立 Thread。
2. 小型调查使用 Local；并行开发使用 worktree。
3. Codex 读取 `AGENTS.md` 和相关模块。
4. 先说明实现方案和风险，再修改。
5. Codex 运行测试、lint 和构建，依据输出修正。
6. 人工在 Diff 面板审查具体变化。
7. 提交、推送并创建 PR。

可直接使用的任务：

```text
目标：为登录接口增加过期令牌的错误处理和回归测试。
范围：只修改认证模块和对应测试；不要重构无关代码。
开始前：读取 AGENTS.md、检查工作区和现有测试模式。
完成标准：
- 过期令牌返回既有错误格式；
- 原有成功路径不变；
- 新旧测试均通过；
- 总结实际 Diff 和未覆盖风险。
不要修改 main；在需要新增生产依赖前先询问。
```

### Codex 自动化做法

适合自动化的不是“任意写代码”，而是边界稳定的维护工作：

- 每日整理失败 CI。
- 检查失效链接。
- 生成发布简报。
- 对新 PR 做仓库规则审查。
- 对依赖告警生成只读审计报告。

官方资料描述的长任务循环是规划、编辑、运行工具、观察、修正、更新状态并重复；worktree、Skills 和 Automations 为这个循环提供隔离与标准化。[OpenAI Developers](https://developers.openai.com/es-419/blog/run-long-horizon-tasks-with-codex)

### 人工检查点

- 需求解释和架构取舍。
- 新依赖、数据库迁移和公开 API 变化。
- 安全、隐私和生产发布。
- Diff 中的范围外修改。
- 测试是否覆盖真实风险，而不是只追求通过。

## 七、场景四：写作与内容生产

### 传统做法

选题、查资料、搭提纲、写初稿、事实核查、编辑、排版、转短视频脚本和归档分别手工完成。资料、草稿和最终稿散落在多个应用里，每次写作都从零开始。

### ChatGPT Project + Codex Project 做法

```text
Project：保存定位、受众、语气和选题路线。
Search：查当前官方资料和案例。
Work：生成文章、演示或视频脚本草稿。
Codex：把确认后的内容写入仓库，检查链接并提交。
Git：保存版本和审查记录。
```

#### 第一步：在 ChatGPT Project 中建立写作上下文

项目指令只保存稳定规则：

```text
读者是刚接触 AI 工作流的中文知识工作者。
文章必须从真实工作问题开始，不按按钮罗列功能。
区分官方事实、实验观察和作者判断。
产品功能必须实时查阅官网并注明访问日期。
避免空泛的“提升效率”，给出输入、步骤、输出和审查点。
```

#### 第二步：研究，而不是直接要求“写一篇文章”

```text
研究主题：ChatGPT Project 与 Codex Project 如何配合完成长期写作。
先不要写正文。
请输出：
1. 读者最可能遇到的五个问题；
2. 当前官方功能和来源；
3. 一个可以真实演示的工作任务；
4. 传统方法、AI 协作和自动化方法的差异；
5. 仍需亲测的问题。
```

#### 第三步：形成可审查文章包

```text
根据已确认研究，创建文章包：
- 一句话观点；
- 详细提纲；
- 1500–2500 字正文草稿；
- 事实核查表；
- 三个标题；
- 一个 60 秒视频脚本。
不要添加研究阶段没有证据的新结论。
```

#### 第四步：交给 Codex 写入仓库

```text
读取仓库 AGENTS.md 和内容目录。
把已确认正文写入 04-cases/[文件名].md，更新对应索引和 CHANGELOG。
检查相对链接、标题层级、重复段落和占位词。
不要改变文章观点；发现事实冲突时停止并列出问题。
完成后给出 Diff 摘要和验证结果。
```

#### 第五步：人工编辑

人工重点不是重新从头写，而是判断：观点是否值得发布、案例是否真实、语言是否像自己、哪些内容可能误导读者。

一次研究应尽量形成多种资产：

| 原始成果 | 可复用资产 |
| --- | --- |
| 官方资料笔记 | 知识卡 |
| 实验过程 | 实验记录 |
| 稳定步骤 | 工作流模板 |
| 真实结果 | 案例文章 |
| 常见问题 | 短视频或 FAQ |

关键是先确认事实和案例，再派生内容，避免让 AI 同时制造“证据”和“结论”。

### 自动化做法

每周自动检查：

- 哪些知识卡超过验证周期。
- 哪些外部链接失效。
- 哪些官方更新影响现有内容。
- 哪些实验完成但尚未转成文章。

自动化只生成候选修改清单；正式内容由人工审查后再合并。

还可以把已经稳定的流程做成两个 Skill：

- `official-product-research`：实时查询官网、生成证据表和待验证项。
- `article-package`：依据已确认研究生成文章、短视频脚本和发布检查表。

Automation 只负责发现“应该更新什么”，不应在无人审查时自动重写并发布文章。

## 八、场景五：个人与团队周报

### 传统做法

周五回忆一周工作，在聊天、邮件、日历、文档和 Git 中逐个寻找记录，再拼成周报。

### Work 做法

```text
从我批准的日历、任务、文档和 GitHub 来源中整理本周工作。
输出：完成事项、产生的结果、阻碍、下周计划和需要管理者决定的问题。
每项成果附来源；不要把讨论当成已完成。
先给我草稿，不要发送。
```

### Scheduled 做法

```text
每周五 16:00 生成周报草稿。
只读取已批准的项目和来源。
没有证据的事项放入“待确认”，不要自动归类为完成。
草稿生成后通知我审查；永远不要自动发送给团队。
```

传统流程中，人花时间找记录；自动化流程中，人只确认结果、语义和是否适合对外表达。

## 九、什么时候不要自动化

- 流程还没有手动成功过。
- 每次输入和判断标准都不同。
- 错误成本高于节省的时间。
- 涉及付款、合同、生产发布、永久删除或敏感外发。
- 数据源不稳定或权限边界没有确认。
- 无法定义“无变化时保持安静”和“失败时通知谁”。

可以使用“三次规则”：同一流程人工或 AI 协作成功三次，输入、步骤和验收标准趋于稳定后，再考虑 Skill 或 Automation。

## 十、把一项工作升级为自动化

### 第一步：测量传统流程

记录耗时、输入、步骤、错误、等待和审批点。没有基线就无法判断 AI 是否真的提效。

### 第二步：让 AI 完成一次成果

使用 Chat、Work 或 Codex，保留人工审查。记录需要反复纠正的内容。

### 第三步：外化规则

- Project instructions：长期目标和输出偏好。
- `AGENTS.md`：仓库命令、约束和完成标准。
- 模板：固定输入和输出结构。
- Skill：稳定的多步骤方法。

### 第四步：连接数据源

使用 Plugin/MCP 连接经过批准的系统。先只读，再逐步增加写权限。

### 第五步：定时运行

设置频率、时区、静默条件、失败通知和审批点。第一次自动运行必须人工全量复核。

### 第六步：评价收益

每月检查：

- 人工耗时是否下降。
- 返工和错误是否增加。
- 无用通知是否过多。
- 是否出现权限扩大和数据泄露风险。
- 自动化是否仍对应真实业务需要。

## 十一、建议的七天上手顺序

| 天 | 实际任务 | 目标级别 |
| --- | --- | --- |
| 1 | 用 Chat 梳理一个真实问题 | L1 |
| 2 | 用 Search 做带来源的研究 | L1 |
| 3 | 用 Work 生成一个可审查文件 | L2 |
| 4 | 建立一个长期 Project | L2 |
| 5 | 用 Codex 完成一个小型仓库修改 | L2 |
| 6 | 把重复规则写入模板或 `AGENTS.md` | L3 |
| 7 | 选择一个低风险流程设计 Scheduled/Automation，但先不自动写入外部系统 | L4 设计 |

不要第一天就追求多 Agent 和全自动。先掌握任务定义、来源边界、结果审查和失败处理。

## 十二、统一任务模板

```text
业务目标：为什么要做。
最终成果：需要什么文件、状态或决定。
输入来源：允许读取哪些资料和系统。
事实边界：哪些是权威来源，哪些只能参考。
范围：包含什么，不包含什么。
质量标准：怎样判断完成。
审批点：哪些动作前必须停下来。
验证：如何检查内容、数据、代码或视觉结果。
失败处理：缺资料、权限不足或结果冲突时怎么办。
```

这个结构比“给我一个好提示词”更重要，因为它同时适用于 ChatGPT Work、Codex、Skills 和 Automations。
