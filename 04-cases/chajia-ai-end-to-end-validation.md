# 差价 AI：从中国市场 Demo 到全球产品的 FDE 交付验证

> 状态：进行中；公开站与本地数据垂直切片已验证，目标云平台完整闭环未验证
>
> 整体证据等级：E0；本地/目标兼容实现：E2；测试站 Web + D1 查询边界：E2
>
> 当前自动化成熟度：M2（自动化链路已在本地和目标兼容层验证，测试站 D1 与查询接口已在线验证，Queue/Cron/Browser Run 仍未在线验证）；目标成熟度：M4
>
> 编写与基线日期：2026-09-25
>
> 环境：Chrome、ChatGPT Sites 登录页、`https://chajia-ai.ixm009.chatgpt.site/`

## 一、案例定位

`差价 AI` 当前是一个持续开发中的 Demo，参考产品为 [OpenTheRank](https://opentherank.com/zh/)。第一阶段面向中国用户，验证用户能否更可信、更低成本地比较 AI 产品在不同地区、渠道和订阅方案下的价格；最终方向是面向全球市场。

本案例验证的不是“AI 能否生成一个网站”，而是 FDE 是否能用 AI 工具完成完整产品闭环：

```text
用户问题
→ 市场与竞品研究
→ 最小产品范围
→ 可信价格数据
→ 交付契约
→ proposal + specs 定义包
→ design + tasks 方案包
→ AI 辅助实现
→ 测试与发布
→ 用户行为与反馈
→ 下一轮产品决定
```

网站只是交付渠道。真正的产品资产是可信数据、清楚的比较标准、可维护的更新流程和经验证的用户决策价值。

### 本案例采用的 AI-native 规范驱动方法

本案例同时参考“AI 原生开发工作流实战”的两讲公开内容：

- [第 17 讲：从模糊想法到清晰的 spec.md](https://time.geekbang.org/column/article/935801)
- [第 18 讲：将规范编译为 plan.md 与 tasks.md](https://time.geekbang.org/column/article/936334)

落地采用 OpenSpec 三阶段：定义包 `proposal + specs` 一次确认产品行为，方案包 `design + tasks` 一次确认技术与执行顺序，随后实现、验收和归档；不逐文件设置审批。通用方法见 [`OpenSpec 三阶段交付法`](../03-workflows/spec-plan-tasks-compilation.md)。

## 二、事实、观察与假设

### 已知事实

- 用户提供的背景：当前产品是 Demo，正在按 FDE 流程持续开发。
- 用户提供的市场策略：第一阶段目标用户是中国用户，最终面向全球。
- 用户提供的参考产品：[OpenTheRank](https://opentherank.com/zh/)。
- 项目采用全线上方式协作；客户沟通使用企业微信，并结合 ChatGPT Project 和代码仓库。
- 当前交付目标是一周内交付中国用户的 AI 订阅价格与可用性查询 MVP；前期交付物为可运行的代码仓库。
- 首批覆盖范围除国际 AI 产品外，包含智谱、千问和火山的相关订阅或产品信息。
- 客户确认所有业务价格必须自动采集，默认每天一次、频率可配置、支持手动触发；合法有效结果自动更新，失败保留上一版有效数据。
- 客户确认 Demo 只用于演示用户体验，不参与技术栈决策。
- 技术方案选择 Astro + Cloudflare Workers/Cron/Queues/Browser Run/D1；选择依据是自动采集核心链路和非功能要求，不是 Demo 或竞品技术。

### 2026-09-25 的直接观察

- `差价 AI` 页面标题为“差价 AI｜全球 AI 订阅价格比较”。
- 未登录访问会进入 ChatGPT 登录页面；登录后的具体功能、数据和用户路径尚未在本案例中完成核验。
- OpenTheRank 公开页面覆盖数字订阅的地区价格比较、币种转换、更新时间、税费说明、搜索、分类、多语言和关注等能力；这些只作为竞品研究输入，不等于 `差价 AI` 必须复制的范围。

### 尚未验证

- 目标 Cloudflare 账户的 Browser Run、Queues 和 D1 实际配额与真实官方页面兼容性。
- 自动采集器对首批官方来源的稳定性、合法访问边界和长期维护成本。
- 中国用户是否存在足够强烈、重复出现的订阅比价需求。
- 用户是否信任当前价格、能否理解税费和订阅周期差异。
- 全球扩张的优先市场、语言、支付与合规要求。

### 2026-10-01 实施观察

- 独立测试站已发布，公开页面在 Chrome/Edge 完成币种、口径隔离、筛选排序、异常状态、移动端、键盘和 SEO 浏览器验证。
- 本地真实 SQLite 已贯通 collector、校验、不可变版本、current、固定精度换算、比较指标和公开 API；写入失败回滚并保留旧 current。
- Queue/outbox 测试暴露并修复了一个通用缺陷：平台投递次数可能随重新发送重置，最大重试必须读取持久化尝试次数，并证明最终只进入一次 dead/DLQ。
- 测试站已创建 D1 `DB` 绑定和 14 张业务表；相同公开价格查询在发布后的 Worker 日志中连续返回 200，原缺少 D1 导致的 503 已消除。价格事实表仍为空，没有用演示数据冒充采集结果。
- Sites 发布器无法接受包含 SQLite trigger 的基线迁移；本地 Wrangler 成功不等于目标发布器成功。最终仅在 Sites 基线排除 trigger，并保留表、外键、CHECK、唯一约束和索引；自动写入上线前仍需验证等价应用层来源链/current 合法性门禁。
- Queue、Cron、Browser Run、Collector Worker 和完整自动采集写入链仍未在线验证，因此不能把 D1 查询恢复表述为云平台闭环验证。
- 官方页面的服务器直连会遇到反自动化挑战；没有合法 Browser Run 证据时来源保持 blocked，不以搜索摘要或人工价格补值。
- API 计价还需要模型/SKU、输入/输出/缓存、单位和阶梯等领域维度；在规范增量完成前，不把 API 价格硬塞进订阅套餐模型。
- 运行控制面已实现 Access JWT 签名与声明校验、operator allowlist、来源启停/频率、手动触发、运行追溯、dead 重试和 current 回退；这些已通过本地真实加密与存储测试，但尚未构成目标 Cloudflare Access/D1 在线证据。
- 公开查询已增加显式字段投影、500 条硬上限、索引计划验证和基于数据投影的 ETag；价格或汇率变化会自然生成新缓存版本，Chrome/Edge 浏览器矩阵 16 项通过。
- 产品目录曾在数据库、API 与 React 中重复维护，已收敛为领域层唯一配置源，并用虚拟产品证明通用采集器和公开查询无需厂商分支；这是“可扩展”从口号转为测试的关键证据。
- JWT 伪造测试曾因只修改 Base64URL 最后字符而偶发等价，修正为翻转解码后的签名字节并重复运行通过；安全反例必须改变真实语义，不能只改变外部编码表示。
- 本机构建会产生带哈希的未跟踪文件；提交时已排除，但也暴露出交付前必须复核构建后 Git 状态并清理/忽略生成物，不能只看测试是否通过。
- 首次平台配置曾使用与 Worker 实际读取名称不同的环境标记，D1 配置也缺少迁移目录；两者均可能通过局部业务测试，但在真实部署中会失效。已增加配置结构负向测试，要求生成配置与运行时接口逐键一致。
- 只有建表迁移时，云端空库没有产品、地区和来源目录，系统无法进入可运营状态。已增加只写目录、不写价格的幂等迁移：来源初始保持 `pending + disabled + unverified`，业务价格仍只能由通过验证的自动采集链路产生。
- 编写可由离场人员执行的 Runbook 反向暴露了初始化缺口；因此运行手册应在最终验收前形成，并由非作者在干净环境执行，而不是在代码完成后补一份概述。
- 原失败测试只组合 collector、数据库和查询 helper，没有经过 Worker 入口，不能证明运行时失败处理。现已由 Worker consumer 驱动真实 SQLite、采集器、版本/current 和公开查询，验证网络超时、解析变化、异常跳变与缺汇率；解析失败也收敛为稳定错误码而不是笼统异常。

因此，在完成实际执行记录前，本文只能作为 **A4 案例设计与执行契约**，不能称为已验证最佳实践。

## 三、第一阶段用户与任务

### 核心用户

第一阶段只聚焦：

> 正在考虑购买 ChatGPT、Claude、Gemini、Cursor 等 AI 产品，关心人民币实际成本、不同地区价格差异和信息可信度的中国个人用户。

暂不同时服务企业采购、跨境支付服务商、所有数字订阅用户或全球多语言用户。

### 首个核心任务

```text
当中国用户准备购买某个 AI 订阅时，
能够在几分钟内看懂不同地区和方案的可比价格、数据时间与限制，
并判断是否值得进一步购买或核实。
```

### 第一阶段不做

- 不承诺用户一定能够跨区购买。
- 不代替官方结账页给出最终含税金额。
- 不提供规避地区、支付、平台或服务条款限制的方法。
- 不为了“看起来全球化”一次性增加大量语言和国家。
- 不在没有来源和更新时间的情况下展示精确价格。

## 四、成功标准

以下是待批准的目标值，不是已测结果：

| 维度 | 第一阶段目标 | 验证方式 |
| --- | --- | --- |
| 用户任务 | 用户能完成一个 AI 产品的地区与方案比较 | 5-10 名目标用户任务测试，记录完成率和阻塞点 |
| 数据可信度 | 每条展示价格都有官方来源、地区、币种、周期、采集器版本和采集时间 | 数据契约、采集器契约测试与抽样核对 |
| 价格准确性 | 当前有效数据来自自动采集并通过来源、字段、口径和异常校验 | 自动校验、异常模拟和真实页面抽样；失败时保留旧值 |
| 可理解性 | 用户能区分月付/年付、原币/换算价、含税/未含税 | 任务测试和理解问题 |
| 效率 | 正常价格更新无需人工操作；新增采集器的人时可测量并逐轮下降 | 记录传统方式、单次 AI 和统一采集器接口的人时 |
| 可复现性 | 另一位执行者能按流程得到同结构结果 | 使用同一数据契约进行复现 |
| 风险 | 失败或异常数据不覆盖上一版有效数据 | 自动校验、幂等、失败注入和恢复测试 |
| 商业信号 | 用户愿意再次使用、关注更新或提出明确需求 | 回访、留存、关注或结构化反馈 |

只有用户任务、数据可信度和持续使用信号同时成立，才能证明这是产品进展，而不只是网站进展。

## 五、一周线上 MVP 交付节奏

此节是本案例的已批准交付节奏；实际完成情况必须在获得真实仓库、客户确认和发布记录后另行记录，不能预填为已完成。

| 时间 | 线上协作与操作 | 当日可确认交付物 | 客户确认点 |
| --- | --- | --- | --- |
| 第 1 天 | 企业微信启动会；审查 Demo、代码仓库与发布权限；冻结 MVP 交付契约 | 范围、验收标准、产品清单、风险清单 | 确认范围与唯一验收人 |
| 第 2 天 | 登记首批官方来源；完成数据契约、技术方案比较、架构 Design 与首个切片计划 | 来源清单、数据契约、已评审 Design | 确认自动采集、币种和技术方案 |
| 第 3 天 | 打通一个产品的“触发 → 自动采集 → 校验 → 当前数据 → API → 页面” | 可运行的纵向切片 | 确认真实数据链路和失败降级 |
| 第 4 天 | 完成产品查询、地区比较、全局币种、来源和更新时间 | 功能候选版本 | 确认价格表达与限制说明 |
| 第 5 天 | 增加其余采集器、调度、重试、控制面、性能和移动端测试 | 自动更新演示与测试报告 | 确认离场后的运行方式 |
| 第 6 天 | 客户验收测试、缺陷修复、发布预演、回滚验证 | 发布候选版本与验收清单 | 签署上线确认或列出阻断项 |
| 第 7 天 | 正式发布或交付可部署仓库；演示自动采集、控制面与恢复流程 | 仓库、部署说明、验收结果、后续待办 | 最终验收确认 |

首批产品的具体套餐、地区和来源必须在第 1 天冻结。若智谱、千问或火山没有公开、可追溯且适合比较的订阅数据，不以猜测补齐；页面应如实显示“暂无可核验价格”或缩小比较范围。

## 六、准备条件

开始第一轮完整验证前需要：

- `差价 AI` 实际源码仓库和本地开发权限。
- 当前部署方式、环境、域名和回滚方式。
- 当前已展示产品和价格数据样本。
- 合法、可引用的价格来源及使用边界。
- 一份中国首阶段用户招募或访谈名单。
- 分析或日志方案；若尚未接入，先用匿名任务测试记录。
- ChatGPT Project（产品研究）和 Codex Project（本地仓库交付），或功能等价的替代组合。

不得把账号密码、会话 Cookie、API Key、个人支付信息或未脱敏用户数据写入 ChatGPT Project、Codex 对话、Git 或案例文档。

## 六、FDE 端到端流程

每次迭代使用唯一交付编号，例如 `DELIVERY-CHAJIA-001`。

### 第一步：冻结 Demo 基线

- **操作位置**：线上 Demo、源码仓库、部署后台和分析工具。
- **输入**：当前页面、功能、数据、已知问题和发布记录。
- **操作**：记录当前用户路径、页面截图、功能清单、技术环境、数据结构、加载和错误情况。
- **输出**：基线报告和已知问题清单。
- **人工审批**：产品负责人确认“当前事实”与“计划能力”没有混写。
- **失败处理**：无法访问源码或部署记录时停止架构判断，只记录外部可观察结果。

### 第二步：验证中国用户问题

- **操作位置**：ChatGPT Project、访谈或任务测试记录。
- **输入**：目标用户假设、现有 Demo、竞品页面和真实购买问题。
- **操作**：访谈或观察用户完成一次订阅比较，记录他们当前查价方式、决策因素、信任障碍和放弃原因。
- **输出**：问题清单、用户语言、优先任务和反证。
- **人工审批**：决定是否继续解决“AI 订阅比价”，以及第一批只覆盖哪些产品。
- **失败处理**：如果用户只需要官方人民币价格而不关心地区比较，应收缩或改变产品命题。

### 第三步：形成首个交付契约

- **操作位置**：ChatGPT Project 起草，人工批准后进入 Git。
- **输入**：用户证据、竞品研究、当前技术约束和成功指标。
- **操作**：定义用户故事、范围、不做事项、核心正常/失败链路、自动化边界、验收示例、数据要求、性能目标、交付方式和恢复条件。
- **输出**：`DELIVERY-CHAJIA-001`。
- **人工审批**：产品范围、价格表达、数据来源和风险必须人工批准。
- **失败处理**：存在“全球平台”之类无法在一轮交付验证的目标时，退回拆分。

### 第四步：建立价格数据契约

- **操作位置**：Git 仓库中的数据契约和测试夹具。
- **输入**：官方价格页、应用商店页面或其他批准来源。
- **操作**：为每条价格定义至少以下字段：

```text
product
plan
platform
region
currency
amount_minor
billing_period
tax_status
source_url
collected_at
collector_key
collector_version
run_id
comparison_key
status
```

- **输出**：机器可校验的数据结构、示例和错误规则。
- **人工审批**：来源边界、税费和周期解释是否准确；正常数据更新不设置逐条人工审批。
- **失败处理**：来源冲突、字段缺失或异常跳变时不替换当前有效数据，记录异常并保留旧值。

### 第五步：由 Codex 实现一个垂直切片

- **操作位置**：连接真实源码仓库的 Codex Project 和隔离分支/worktree。
- **输入**：批准的交付契约、spec、数据契约、现有代码和 `AGENTS.md`。
- **操作**：先比较候选技术方案并完成 Design 评审，再实现一个完整切片：“手动或定时触发一个官方来源 → 自动采集与校验 → 更新当前有效数据 → 展示地区原价、所选全局币种价、来源和时间 → 失败时保留旧值”。
- **输出**：代码、测试、Diff、运行说明和已知限制。
- **人工审批**：数据解释、界面表达、隐私、安全和范围偏差。
- **失败处理**：测试不通过、数据契约不满足或 Diff 超出范围时不得发布。

### 第六步：执行发布前验证

- **操作位置**：CI、预览环境和浏览器。
- **输入**：候选版本和批准的数据样本。
- **操作**：执行数据校验、单元测试、关键路径测试、移动端检查、无障碍基础检查、链接检查和内容复核。
- **输出**：发布证据包。
- **人工审批**：抽样核对展示价格与权威来源；确认免责声明和更新时间清楚可见。
- **失败处理**：关键价格错误、来源缺失或周期混淆属于阻断发布问题。

### 第七步：受控发布与回滚

- **操作位置**：实际部署系统。
- **输入**：通过门禁的候选版本、变更摘要和回滚方案。
- **操作**：发布后立即执行冒烟测试，核对首页、比较路径、数据加载和错误状态。
- **输出**：发布编号、时间、版本、检查结果和回滚状态。
- **人工审批**：生产发布和任何数据迁移。
- **失败处理**：关键路径失败或数据错误时回滚到上一安全版本，并建立事故记录。

### 第八步：观察产品结果

- **操作位置**：匿名分析、用户测试、反馈记录和 ChatGPT Project。
- **输入**：任务完成率、搜索或比较行为、退出点、反馈和支持问题。
- **操作**：判断用户是否找到目标产品、是否理解比较结果、是否信任数据以及下一步做了什么。
- **输出**：`OUTCOME-CHAJIA-001`，包括结果、偏差和下一轮建议。
- **人工审批**：下一轮优先级和是否继续投入。
- **失败处理**：无用户证据时，不以页面上线替代产品验证。

### 第九步：全球化门禁

只有满足以下条件才进入全球扩张：

1. 中国首阶段的核心任务已达到约定成功标准。
2. 价格采集、校验和过期处理不依赖不可持续的人工劳动。
3. 已通过研究选择明确的第二市场，而不是笼统“支持全球”。
4. 能处理目标市场语言、币种、税费、数据来源、隐私和法律差异。
5. 有按地区分批发布和回滚的能力。

全球化顺序应为：

```text
中国用户验证
→ 选择一个第二市场
→ 本地化与数据可靠性验证
→ 复用交付系统
→ 再决定多市场扩张
```

## 九、五种工作方式对比

| 阶段 | 做法 | 主要问题 | 本案例如何验证 |
| --- | --- | --- | --- |
| 传统手工 M0 | 人工查价、整理、修改页面和发布 | 慢、易过期、标准不一致 | 记录新增一个产品的完整人时和错误 |
| 单次 AI 辅助 M1 | 临时让 AI 搜集资料或改页面 | 来源不可控、结果难复用 | 保留当前 Demo 的实际过程作为基线 |
| 标准化 M2 | 使用交付契约、数据契约、Design 和固定测试 | 仍需人工执行更新 | 验证契约和架构是否可复用 |
| 半自动化 M3 | 自动采集候选，人工决定是否更新 | 仍有日常审批负担 | 只作为迁移对照，不是本期目标 |
| 受控自动化 M4 | 自动采集、校验、更新和监控；人只处理异常与程序变更 | 必须有幂等、异常隔离和恢复 | 本期目标；连续运行和失败注入验证 |

## 十、常见失败与处理

| 失败 | 发现方式 | 处理 |
| --- | --- | --- |
| 价格过旧 | 超过来源的新鲜度阈值 | 自动重试；继续展示旧值并标明最后成功时间 |
| 月付和年付混比 | 数据契约校验 | 拒绝进入同一比较组 |
| 汇率变化造成排名误导 | 显示汇率时间并重算 | 保留原币，换算价只作参考 |
| 税费口径不同 | 税费字段缺失或冲突 | 明确含税状态；不确定时标为未知 |
| AI 生成了无来源价格 | 来源字段为空 | 拒绝进入 current，不允许模型补猜 |
| 用户只看到最低价而忽略限制 | 用户测试和行为数据 | 在比较结果旁展示渠道、地区和限制 |
| 过早全球化 | 多语言功能增加但核心任务未验证 | 回到中国首阶段指标，冻结扩张 |
| 页面发布但无人使用 | 没有任务完成和复访信号 | 继续用户发现或调整问题，不扩功能 |

## 十一、人工决策点

以下事项不能交给自动化独立决定：

- 用户问题、市场定位和商业优先级。
- 是否可以使用某个价格来源。
- 税费、订阅周期和购买限制的最终解释。
- 数据冲突和异常价格处理。
- 生产发布、回滚和安全事件。
- 是否从中国市场进入第二市场。
- 是否将用户行为数据用于新的目的。
