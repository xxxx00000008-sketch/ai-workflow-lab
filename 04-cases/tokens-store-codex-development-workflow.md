# 自动化案例：用 Codex 持续开发 Token 聚合平台

> 状态：未验证
>
> 编写日期：2026-09-19
>
> 适用环境：`tokens-store` Git 仓库、ChatGPT 桌面端 Codex、本地开发环境、Git 远端

## 使用者与真实任务

- 使用者：个人开发者，主要由 Codex 完成功能开发和 Bug 修复。
- 当前状态：代码已克隆到本地 `tokens-store` 目录，并作为本地文件夹加入同名 Codex Project。
- 原有困难：产品资料来自不同位置，没有统一入口；每次开发都需要重新解释背景；功能需求、Bug、代码变更和验收结果之间缺少稳定关联。
- 成功标准：任何一个需求都能从原始产品资料进入明确任务，经过隔离开发、自动验证和人工审查，最后形成可追踪的提交或 PR。

## 结论

不需要重建仓库，也不需要为“看起来规范”而创建大量目录。现有的 `Git 仓库 + Codex Project` 可以继续使用，重点补齐五层：

1. **产品资料入口**：先建立资料索引，不急着搬运所有原文。
2. **持久开发规则**：用根目录 `AGENTS.md` 保存每次任务都要遵守的规则。
3. **标准任务单**：功能和 Bug 使用不同模板，一个 Codex 任务只处理一个结果。
4. **隔离与验证**：写入任务优先使用 worktree，完成后检查测试和 Diff。
5. **经验复用**：重复稳定后再升级为 Skill 或定时检查。

当前最大的瓶颈不是 Codex 写代码的能力，而是产品资料没有形成“本次改什么、为什么改、怎样才算完成”的权威输入。

## 自动化目标

把当前的临时协作：

```text
收到零散文档 → 临时告诉 Codex → Codex 改代码 → 人工凭印象判断
```

升级为：

```text
零散资料
  ↓ 登记来源和状态
需求简报 / Bug 单
  ↓ 人工确认范围与验收标准
Codex 计划
  ↓ 人工批准方案
独立 worktree 实现
  ↓ 测试、安全检查、Diff 审查
Commit / PR
  ↓ 更新需求状态和必要文档
发布或合并
```

## 准备条件

- `tokens-store` 已是正常 Git 仓库，并有明确的主分支。
- 本地能够运行项目的安装、启动、测试和检查命令。
- Codex Project 的主文件夹设置为 `tokens-store` 仓库根目录。
- 产品资料可以被引用：本地文件、在线文档链接、聊天记录或截图均可，但必须标出来源和日期。
- 使用测试账号、测试 Token 和脱敏数据；不要让 Codex 接触生产密钥或真实客户凭据。

## 第一步：先做一次只读项目体检

新建一个 Codex 任务，选择 Local，只调查、不修改：

```text
请只读分析当前 tokens-store 仓库，不要修改文件。

输出：
1. 技术栈、启动方式、测试方式和构建方式；
2. 主要目录及职责；
3. Token 接入、存储、路由、计费、权限和日志相关代码分别在哪里；
4. 当前产品文档、README、注释和配置之间有哪些冲突或缺口；
5. 进行功能开发和 Bug 修复前，最需要固化的仓库规则；
6. 当前 Git 状态和明显风险。

不要根据文件名猜结论；引用具体文件路径和代码位置。
```

人工检查：确认 Codex 找到的启动、测试和业务模块位置准确。错误结论先纠正，不要立即让它创建规范文件。

输出：一份当前状态报告，作为后续整理 `AGENTS.md` 和产品资料索引的依据。

## 第二步：给零散产品资料建立唯一入口

不必把所有产品文档复制进仓库。先建立一张产品资料索引，每条资料只记录：

| 字段 | 说明 |
| --- | --- |
| 编号 | 例如 `PRD-012`、`BUG-037` |
| 名称 | 资料或需求名称 |
| 原始来源 | 文件路径或在线链接 |
| 日期/版本 | 防止使用过期资料 |
| 状态 | 草稿、已确认、已废弃 |
| 影响模块 | 接入、Token 池、路由、计费、后台等 |
| 权威级别 | 哪份资料冲突时优先 |
| 待确认问题 | 开发前必须由人回答的问题 |

规则：

- 原始资料继续留在原系统，索引只负责定位和判断权威性。
- 每次开发只引用本任务需要的资料，不把整个产品资料库塞进上下文。
- 多份文档冲突时，由人确认结论并记录决定，Codex不能自行选择业务规则。
- 功能开发前，把原始资料压缩成一页“需求简报”；Bug 修复前形成可复现的 Bug 单。

## 第三步：用 `AGENTS.md` 固化长期开发规则

根目录 `AGENTS.md` 只保存跨任务稳定的内容：

```markdown
# AGENTS.md

## Project purpose

一句话说明 tokens-store 服务什么用户、解决什么问题。

## Repository map

列出入口、核心服务、测试、迁移和文档位置。

## Development commands

写明安装、启动、测试、lint、构建和数据库迁移命令。

## Product rules

- 需求必须引用已确认的产品资料编号。
- 文档冲突时停止实现并列出冲突，不自行决定业务规则。

## Security rules

- 禁止读取、输出或提交生产 Token、密钥和客户数据。
- 测试使用假数据或专用测试凭据。
- 涉及鉴权、计费、配额和数据删除的变更必须人工审查。

## Definition of done

- 验收标准逐项满足。
- 相关测试通过。
- 检查失败路径、日志脱敏和兼容性。
- 审查 Diff，不修改任务范围外文件。
```

不要把具体需求写进 `AGENTS.md`。具体需求放在当前任务单；当 Codex 连续两次犯同类错误时，再考虑把对应规则加入 `AGENTS.md`。

## 第四步：统一功能开发入口

一个功能使用一个 Codex 任务。需求不清楚时先使用 Plan 模式，只输出方案，不修改代码。

```text
任务类型：功能开发
需求编号：PRD-012
目标：支持按供应商和模型配置 Token 路由优先级。
产品来源：<文档路径或链接>
影响范围：<已知模块；未知时先调查>
不在范围：计费规则、历史数据迁移。

验收标准：
1. ...
2. ...
3. ...

约束：
- 遵守 AGENTS.md；
- 不读取或输出真实 Token；
- 不增加生产依赖，除非先说明必要性并获得确认；
- 保持现有接口兼容。

先完成：
1. 读取需求和相关代码；
2. 列出歧义、风险和受影响文件；
3. 给出实现及测试计划；
4. 等我确认后再写代码。

完成时输出：变更摘要、验收标准对应关系、测试结果、风险和待人工检查项。
```

人工批准计划后，再让同一任务继续实现。这样保留了需求澄清和技术决策的连续上下文。

## 第五步：统一 Bug 修复入口

Bug 任务先复现，再修复；禁止看到报错后直接猜改代码。

```text
任务类型：Bug 修复
Bug 编号：BUG-037
现象：<用户看到了什么>
期望行为：<正确结果>
实际行为：<错误结果>
复现环境：<版本、配置、入口>
复现步骤：
1. ...
2. ...

证据：<脱敏日志、截图或失败测试>
相关产品规则：<文档编号或链接>

要求：
1. 先稳定复现，无法复现时停止并说明还缺什么；
2. 找到根因，不只屏蔽错误；
3. 先补能失败的回归测试，再进行修复；
4. 运行受影响测试和必要的全量检查；
5. 检查相邻路径是否有同类问题；
6. 不输出真实 Token、请求头或客户数据。

完成时输出：复现结果、根因、修复、测试证据、影响范围和回滚方法。
```

## 第六步：选择 Local 或 Worktree

| 任务 | 建议环境 | 原因 |
| --- | --- | --- |
| 只读调查、定位代码、复现依赖当前本地服务的问题 | Local | 直接使用当前工作环境 |
| 新功能、重构、有明确写入的 Bug 修复 | Worktree | 与日常工作隔离，方便审查和放弃 |
| 两个互不依赖的需求并行 | 每个需求一个 worktree | 避免任务相互覆盖 |
| 必须使用当前未提交改动的紧急问题 | Local | worktree 默认不包含全部本地状态 |

开始写入前检查：

1. 主分支是否最新。
2. 当前工作区是否有未提交修改。
3. 本任务从哪个分支或提交开始。
4. worktree 是否具备依赖和测试配置。
5. 是否错误复制了真实密钥或生产配置。

Codex 官方文档说明，worktree 为同一仓库提供独立 checkout，适合并行任务；Local 与 worktree 之间可以移交任务。被忽略文件不会自动全部移动，需要单独准备环境。对于 Token 平台，应优先使用测试配置和假密钥，不要通过便利配置扩大生产凭据暴露范围。

## 第七步：执行统一交付闭环

Codex 每次写入任务都执行：

```text
读取 AGENTS.md 和任务资料
  ↓
检查 Git 状态与任务范围
  ↓
先计划，确认歧义
  ↓
实现最小完整改动
  ↓
运行定向测试
  ↓
运行 lint、类型检查、构建或必要全量测试
  ↓
检查安全、日志脱敏、兼容性和失败路径
  ↓
审查 Diff
  ↓
Commit / Push / PR
  ↓
人工验收与合并
```

人工审查重点：

- 是否严格符合产品规则，而不是只让测试通过。
- 是否出现 Token、密钥、请求头或客户数据泄漏。
- 是否改变路由、配额、计费、鉴权或数据删除行为。
- 是否修改任务范围外文件。
- 是否存在静默失败、无限重试、日志泄密或兼容性回退问题。

## 第八步：稳定后再升级为 Skill 和 Automation

当功能开发或 Bug 修复流程至少重复成功三次，再考虑：

- `feature-delivery` Skill：读取需求简报、检查歧义、制定计划、实现、验证并生成交付摘要。
- `bug-fix` Skill：复现、定位根因、补回归测试、修复并检查相邻问题。
- 每周只读 Automation：汇总失败 CI、长期未关闭 Bug、过期产品资料和近期高风险变更。

Automation 初期只报告，不自动修改、提交或合并。涉及生产 Token、供应商配置、计费和权限的操作始终保留人工审批。

## 建议目录结构（无需创建）

```text
tokens-store/
├── AGENTS.md                       # Codex 长期开发规则
├── README.md                       # 项目入口与本地启动方法
├── docs/
│   ├── product/
│   │   ├── index.md                # 零散产品资料的统一索引
│   │   ├── glossary.md             # Token、渠道、供应商、配额等统一术语
│   │   ├── requirements/           # 已确认的一页需求简报
│   │   └── decisions/              # 产品冲突的最终决定
│   ├── architecture/
│   │   ├── system-overview.md      # 关键模块、数据流和外部依赖
│   │   └── adr/                    # 重要技术决策
│   └── runbooks/
│       ├── local-development.md    # 本地运行与测试
│       ├── release.md              # 发布和回滚
│       └── incident.md             # 故障排查与应急步骤
├── .agents/
│   └── skills/
│       ├── feature-delivery/       # 稳定后再建立的功能交付 Skill
│       └── bug-fix/                # 稳定后再建立的修 Bug Skill
├── .codex/                          # 可选的本地环境和常用 Actions
├── src/                             # 现有业务代码，按实际项目为准
└── tests/                           # 现有测试，按实际项目为准
```

这只是目标信息结构，不要求一次创建，更不需要创建空文件。建议按真实需求逐步出现：先有 `AGENTS.md` 和产品索引；第一份确认需求到来时再出现需求简报；流程稳定后再建立 Skills。

## 实施顺序

### 第一阶段：立即执行

1. 完成只读项目体检。
2. 确认产品资料权威顺序并建立索引。
3. 根据真实命令整理最小 `AGENTS.md`。
4. 从下一项功能或 Bug 开始使用标准任务单。
5. 写入任务默认使用独立 worktree，并强制测试和 Diff 审查。

### 第二阶段：累计三个任务后

1. 统计每次重复输入和 Codex 常犯错误。
2. 更新 `AGENTS.md`，删除无效规则。
3. 将稳定的功能开发或 Bug 修复步骤封装为 Skill。
4. 建立只读周检 Automation。

### 暂时不要做

- 不要一次性重构整个仓库目录。
- 不要把所有产品原文复制进 Git 造成多份真相。
- 不要让一个 Codex 任务同时处理多个无关功能和 Bug。
- 不要在流程尚未稳定时自动提交、合并或部署。
- 不要让 Codex访问生产 Token 或真实客户数据。

## 预期结果

- 产品资料虽然仍可能分散，但每项开发都能追溯到权威来源。
- Codex 不再依赖你每次重复说明启动、测试、安全和交付规则。
- 功能和 Bug 都有明确范围、验收标准、测试证据与回滚思路。
- 并行任务不会直接污染本地工作区。
- 重复流程在验证稳定后才能进入 Skill 和 Automation。

## 常见失败与处理

| 失败情况 | 如何发现 | 处理方法 |
| --- | --- | --- |
| 产品文档互相冲突 | 同一业务规则出现不同结论 | 停止实现，由人确认并记录决定 |
| Codex 修改范围过大 | Diff 出现无关文件 | 缩小任务，丢弃无关改动后重做 |
| Bug 没有稳定复现 | 修复前没有失败测试或复现记录 | 补环境和证据，无法复现则不宣称修复 |
| worktree 无法运行 | 缺少依赖、配置或本地服务 | 配置安全的 setup，使用测试配置，不复制生产秘密 |
| `AGENTS.md` 越写越长 | 规则重复、相互冲突 | 保留稳定规则，把具体流程移到文档或 Skill |
| 自动化产生危险修改 | 定时任务直接写代码或推送 | 退回只读报告，所有高风险动作人工审批 |

## 传统做法与优化后对比

| 对比项 | 当前做法 | 优化后 |
| --- | --- | --- |
| 产品资料 | 临时查找、临时解释 | 索引定位，需求简报确认本次权威输入 |
| Codex 上下文 | 每个任务重复说明 | `AGENTS.md` 保存长期规则，任务单保存本次目标 |
| 功能开发 | 直接聊天后改代码 | 先计划和确认验收，再在 worktree 实现 |
| Bug 修复 | 根据现象猜测修改 | 复现、回归测试、根因、修复、相邻检查 |
| 验收 | 看最终回答 | 对照验收标准、测试结果和 Diff |
| 并行工作 | 共用本地目录 | 一个独立任务对应一个 worktree |
| 自动化 | 每次手工提醒 | 稳定后使用 Skill；周期任务先只读报告 |

## 适用限制

- 本文没有读取 `tokens-store` 的实际代码、技术栈、测试命令和产品文档，因此状态为“未验证”。
- 目录名称和命令必须由第一次只读体检根据真实仓库修正。
- 如果仓库不是单体项目，子模块可能需要更靠近代码的 `AGENTS.md` 或覆盖规则。
- 如果产品资料位于需要登录的外部系统，应先确认权限和数据政策，再决定使用连接器或 MCP，不能默认让 Codex 全量读取。

## 官方依据

- [Codex 最佳实践](https://developers.openai.com/guides/best-practices)：建议明确目标、上下文、约束和完成条件；把长期规则放入 `AGENTS.md`，重复流程稳定后再升级为 Skill 和计划任务。
- [Codex Projects](https://developers.openai.com/docs/projects)：本地项目的主文件夹用于 Git 操作以及自动发现 `AGENTS.md`、Skills 和配置。
- [Codex Worktrees](https://developers.openai.com/zh-Hans/docs/environments/git-worktrees)：worktree 支持同一仓库中的隔离并行任务以及 Local/Worktree 移交。
- [使用 `AGENTS.md` 配置 Codex](https://developers.openai.com/docs/agent-configuration/agents-md)：根目录规则可与更具体的子目录规则分层应用。
- [创建 Skills](https://developers.openai.com/docs/build-skills)：Skill 用于封装可重复的指令、资源和可选脚本。
