# AI-native 项目启动工具包

> 用法：新项目按顺序复制相应模板，填写后放入客户授权的系统或实际项目仓库。不要把客户原始内容提交到 `ai-workflow-lab`。

## 1. 项目启动摘要

```text
项目名称：
客户目标：
目标用户：
用户必须完成的一个核心任务：
一周/本期交付物：
明确不做：
唯一验收人：
需求联系人：
仓库负责人：
发布负责人：
截止时间：
现有 Demo / 仓库 / 环境：
缺失权限与阻塞：
```

AI 的作用：把客户材料整理为草稿、发现矛盾和缺失项。人工控制点：客户目标、范围、联系人和权限必须由客户确认。

## 2. 工具与信息归属表

```text
企业微信：客户确认、进度、演示、验收
ChatGPT Project / Work：研究、分析、方案和决策摘要
Git 仓库：批准的交付契约、代码、测试、部署说明
Codex：读取仓库、实现、测试、Diff 审查
预览环境：每日演示和客户验收
生产环境：经批准的正式发布
```

为每项补充实际链接、负责人和权限。密钥只进入批准的密钥管理系统，不进入本表。

AI 的作用：把已确认信息转换为可测试行为，指出不可验收的表述。人工控制点：范围、事实来源、风险、发布和批准。

## 4. OpenSpec 两个实施前审查包

OpenSpec 仍使用 proposal、specs、design、tasks，但项目只做两次实施前审查：需求包 `proposal + specs`，方案包 `design + tasks`。不逐文件审批。

### `proposal.md`：变更提案

```text
Change ID（动词开头的 kebab-case）：
为什么现在要做：
这次改变什么：
明确不做什么：
新增 capability：
修改 capability：
影响的用户、数据、系统或运营角色：
```

人工门禁：两分钟内能够说清为什么做、改什么、不改什么；多个可独立验收的目标应拆分。

### `spec.md`：需求规范

```text
规范编号与状态：
上游交付契约：
目标用户与核心问题：
成功条件：

已确认事实：
推断：
待确认问题：

Capability / Purpose：
Requirement（系统必须表现的可观察行为）：
Scenario（GIVEN / WHEN / THEN）：
正常、空、错、过期、无权限和失败场景：
外部安全、隐私、可靠性、兼容性或可访问性约束：
明确不做：

变化类型：ADDED / MODIFIED / REMOVED / RENAMED
需求到交付契约的映射：
客户确认记录：
```

人工门禁：每项 requirement 至少有一个 scenario；需求、非范围和场景无冲突；客户确认“做什么”和“怎样验收”；不得在本文件决定技术框架。

### `design.md`：技术方案（旧项目可沿用 `plan.md`）

```text
方案编号与状态：
上游 spec：
目标、非目标与技术约束：
已观察事实、负责人确认、推断和开放项：

项目类型：新项目无技术栈 / 新项目技术栈已指定 / 既有项目增量 / 架构演进
目标 Demo 的作用：仅 UX/验收输入 / 明确要求继承的生产系统（附运行证据）
候选技术方案：
候选方案评价维度：
最终语言、框架、运行时、存储、异步任务、部署和测试选型：
被否决方案与原因：
重新评估技术选型的触发条件：

核心正常链路：
异常、超时、重复、部分失败和恢复链路：
模块边界与依赖方向：
数据所有权、状态机、幂等和一致性：
异步可靠性（如适用）：事务边界、唯一重试权威、持久化尝试次数、确认时点、退避/最大次数、死信/重放、幂等键、模糊失败窗口及回归测试
应用、数据和部署架构：
身份、权限、安全与隐私边界：
日志、指标、追踪、告警和运行手册：

容量模型与当前假设：
用户可感知的性能目标：
缓存、索引、分页、限流和并发策略：
预期瓶颈与压测方法：
扩展产品、地区、租户、数据源或业务类型的方式：
持续增长目录的唯一配置源及消费者：
虚拟条目扩展契约测试（证明主链路无类型/厂商分支）：
当前架构上限和触发升级的可观察阈值：

测试策略与首个垂直切片：
迁移、部署、回滚和恢复方式：
首次初始化分类：系统目录/配置种子；自动产生且禁止预填的业务事实；禁止入库/入仓库的秘密或客户数据
空环境启动证据：配置键一致性、迁移目录、迁移执行、最小目录生成、业务事实为空
风险、取舍和缓解：
技术工作到 FR/AC 编号的映射：
FDE 离场后的长期运营者：
持续变化数据或内容的产生、更新和异常处理方式：
环境能力矩阵（本地 / 测试 / 生产）：
端口与适配器边界及替换条件：
测试环境证据：
生产上线前额外门禁与未验证能力：
仍会改变技术选型的开放项：
FDE 确认记录：
```

人工门禁：方案足够简单、可运行、可测试，没有新增未批准范围；已说明动态核心链路、数据来源和长期责任；已比较环境能力并定义端口/适配器；核心链路与异常链路完整；测试证据和生产上线门禁分开；会改变 spec、方案或任务拆分的问题必须先关闭。

### `tasks.md`：原子任务

```text
任务编号：
关联 FR / AC：
依赖：
允许修改的文件或模块：
执行动作：
验证命令或人工步骤：
完成证据：
证据覆盖层级：单元 / 契约 / 真实存储 / 异步运行 / API / 浏览器 E2E / 目标平台
执行环境与时间：
证据位置：
复核人：
证据失效条件：
构建后工作区状态（生成物、缓存、测试报告是否被忽略或明确纳入交付）：
负责人：
状态：待执行 / 进行中 / 阻塞 / 完成
```

人工门禁：任务依赖正确、每个任务可独立验证、每个验收场景有任务覆盖。完整方法见 [`OpenSpec 三阶段交付法`](../03-workflows/spec-plan-tasks-compilation.md)。

## 6. 客户验收清单

```text
版本或提交：
预览/生产地址：
验收人：
验收时间：

[ ] 核心用户路径可完成
[ ] 三个验收示例符合交付契约
[ ] 主要错误和空状态可理解
[ ] 数据、来源和关键文案已核对
[ ] 移动端或约定设备可用
[ ] 已知限制已经说明
[ ] 启动、部署与回滚说明可用
[ ] 持续运行项目已验证一次自动执行、一次手动触发及失败恢复
[ ] 失败切片从真实运行入口贯穿持久状态与用户入口，并断言稳定错误码和最后正确状态
[ ] 从干净检出按 README 完成安装、配置、初始化、构建、启动和最小路径
[ ] 运行手册覆盖角色、资源、配置、迁移/初始数据、部署顺序、触发、监控告警、恢复、回滚和扩展
[ ] 首次初始化无需作者隐藏操作；系统目录可生成，业务事实仍由批准的运行链路产生
[ ] 每项“已完成”都有匹配层级、环境、时间和位置的证据
[ ] 安全反例改变了解码后的真实字节/语义，不依赖可能等价的编码字符变化
[ ] 构建后 Git 状态无意外生成物、缓存、测试报告或哈希文件

阻断问题：
非阻断问题：
验收结论：通过 / 有条件通过 / 不通过
客户确认记录：
```

## 7. AI-native 复盘

```text
哪一步最耗时，为什么：
哪一次 AI 输出造成返工，为什么：
哪一项人工确认避免了风险：
哪些上下文未能正确交接：
哪些检查可以模板化或自动化：
新人最容易卡在哪里：
本次应修改的 ai-workflow-lab 文件：
可升级为模板 / Skill / Automation 的内容：
不得沉淀的客户敏感内容：
```

复盘完成的标志不是写完总结，而是至少更新一条可复用规则、模板或失败处理；如果本次没有可靠证据，则只记录“待验证”，不包装成最佳实践。
