# ChatGPT Projects

> 状态：第一轮已验证
>
> 最近验证：2026-09-19
>
> 环境：ChatGPT Project、Codex 桌面端、GitHub 仓库

## 一句话结论

ChatGPT Projects 适合把一个持续目标所需的对话、文件、指令和相关上下文集中在一起；它解决的是工作连续性和上下文组织问题，不替代 Git 的版本控制，也不保证模型自动掌握所有项目内容。

## 能解决什么问题

- 长期研究、写作、规划等任务需要多次返回时，减少重复交代背景。
- 把围绕同一目标的对话、参考文件和项目指令放在一个工作空间中。
- 为重复产出提供较一致的背景和响应规则。
- 在支持的方案中，与协作者共享项目上下文。

OpenAI Academy 将 Projects 定义为围绕特定工作或关注领域的专用空间，可以集中 chats、files、instructions 和相关 context，并建议在研究、写作、周期性规划等持续工作中使用。[来源 1](https://openai.com/academy/projects/)

## 不适合什么场景

- 一次性、上下文很少的快速问答：普通对话成本更低。
- 需要严格版本历史、差异审查、冲突合并或可回滚文件状态：应使用 Git 或其他专业系统。
- 希望“上传后永久自动保持最新”的资料库：项目资料仍需要人为维护、标注日期和淘汰过期信息。
- 仅靠记忆就要求精确复现关键事实：重要状态应写入可检查的项目文件。

## 核心模型

一个可维护的 Project 可以拆成四层：

| 层 | 内容 | 维护方式 |
| --- | --- | --- |
| 目标 | 项目要解决什么问题、当前阶段是什么 | 写入项目说明和仓库 README/Roadmap |
| 规则 | 语气、质量标准、隐私与协作边界 | 写入项目指令和 `AGENTS.md` |
| 事实 | 资料、决策、实验数据和当前状态 | 保存在可追踪文件中，注明来源与日期 |
| 过程 | 探索、讨论、临时推理 | 留在对话中，有价值时再沉淀为文件 |

Project 是上下文容器；仓库是事实和版本的权威记录。关键结论从对话沉淀到仓库后，才进入可审查、可复用状态。

## 指令、文件、对话和记忆的分工

| 载体 | 适合保存 | 不应依赖它保存 |
| --- | --- | --- |
| 项目指令 | 稳定目标、协作规则、输出标准 | 经常变化的事实和大段参考资料 |
| 项目文件 | 权威资料、状态、模板、交付物 | 没有日期和来源的临时判断 |
| 项目对话 | 探索过程、任务执行、澄清记录 | 唯一一份关键决策或最终成果 |
| Project memory | 跨对话连续性和相关历史 | 必须逐字准确、可审计的项目状态 |

官方资料说明，project-only memory 会限制上下文边界：项目内对话可引用同一项目内的其他对话，但不能引用项目外对话；具体可用性取决于方案与设置。[来源 1](https://openai.com/academy/projects/) [来源 2](https://academy.openai.com/en/public/clubs/work-users-ynjqu/resources/projects)

## 推荐用法

1. 一个 Project 对应一个长期目标，而不是一种宽泛工具。
2. 初始化时写清目标、非目标、交付物、质量标准和隐私边界。
3. 将稳定规则写入项目指令，将可审计状态写入仓库。
4. 每次对话只处理一个可验收任务，并引用相关文件。
5. 对话结束时，把决策、证据和交付物沉淀到文件。
6. 定期清理重复、冲突和过期上下文。

完整流程见 [`ChatGPT Project 生命周期`](../../03-workflows/chatgpt-project-lifecycle.md)。

## 选择指南

| 情况 | 建议 |
| --- | --- |
| 一次性问题，完成后无需延续 | 普通对话 |
| 多次返回同一目标，需要共享资料与规则 | ChatGPT Project |
| 修改代码或仓库文件，需要测试与版本记录 | Project + Codex + Git |
| 涉及客户隔离或敏感工作流 | 独立 Project；可用时选择 project-only memory，并遵循组织政策 |

## 限制、风险与隐私

- 功能、共享权限和文件限制可能因方案、工作区和时间而变化。
- 上下文可用不等于每次回答都会使用全部上下文；重要资料仍应在任务中明确引用。
- 共享 Project 中的资料和对话可能对协作者可见；加入前应先移除无关的个人或客户数据。
- project-only memory 是上下文隔离机制，不应被当作完整的数据安全或合规方案。
- 删除、保留、训练使用等数据政策应在实际账号的官方设置和组织政策中单独确认。

## 待验证问题

- 不同订阅和工作区的文件数量、大小、工具与共享限制。
- 默认 memory 与 project-only memory 在当前个人账号中的逐项对照。
- 项目指令、全局自定义指令与单次任务指令冲突时的实际优先级表现。
- 共享 Project 的角色权限、成员移除和资料可见性边界。

这些问题不影响本轮关于“长期项目容器和仓库协作模式”的结论，但需要在对应账号环境中继续实测。
