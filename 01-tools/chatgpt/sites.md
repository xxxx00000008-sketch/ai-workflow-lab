# ChatGPT Sites

> 状态：第一轮完成
>
> 最近验证：2026-09-19
>
> 依据：官方 OpenAI Docs；当前仓库尚未执行实际 Sites 部署

## 一句话结论

Sites 是 ChatGPT 内置的网站托管能力，可以从提示或兼容的本地项目创建、保存、部署、迭代并分享网站、Web 应用和游戏，不需要另外配置一套托管流程。

它不是普通的“网页预览”，也不是 ChatGPT Project：

- **预览**用于在发布前检查结果。
- **Site** 是可以持续管理和分享的托管产物。
- **ChatGPT Project** 用于组织对话、文件和指令。
- **本地项目**保存可通过 Git 审查的源代码。

## 当前可用性

根据 2026-09-19 查阅的 OpenAI Docs，Sites 处于公开 Beta，并面向 ChatGPT Plus、Pro、Business、Enterprise 和 Edu 方案开放；具体使用量和账号可见性仍受方案、工作区设置与逐步发布影响。

Sites 可以在 ChatGPT 桌面应用中创建和管理，也可以从网页版的 Sites 入口管理。CLI 和 IDE 扩展没有独立的 Sites 管理界面，但仍可以编辑和测试关联的本地源码。

## 适合解决什么问题

- 把一个想法快速变成可分享的落地页或信息网站。
- 为团队建立项目看板、申请表、内部工具或计算器。
- 把数据和流程包装成轻量 Web 应用。
- 创建可交互的教学资源、展示页面或小游戏。
- 将兼容的本地项目连接到托管环境。

## 不适合什么场景

- 需要完全控制基础设施、区域、网络、运行时和部署流水线。
- 已经有成熟云平台、CI/CD、监控和域名治理的大型生产系统。
- 发布前必须经过独立预览环境、分阶段放量或复杂审批的场景。
- 处理受监管或敏感数据，但尚未确认工作区政策和存储边界。

## 如何创建

可以在提示中明确使用 `@Sites`，也可以直接说明要创建 `website`。

一个有效的请求至少包括：

```text
为谁创建：目标用户和访问权限。
解决什么问题：主要任务和成功标准。
核心体验：页面、表单、筛选、计算或交互。
数据来源：附件、本地项目、连接系统或人工输入。
持久化要求：哪些数据需要跨访问保留。
视觉约束：品牌、布局、移动端和无障碍要求。
发布边界：先保存供审查，不要直接部署。
```

示例：

```text
@Sites 创建一个 AI 工作流实验看板。
读者可以按工具、场景和难度筛选工作流，并打开对应的 GitHub 文档。
先生成并保存可审查版本，不要部署。确认移动端布局、链接和空状态后再询问我是否发布。
```

## 保存、部署与生产风险

官方文档特别说明：每个 Sites 部署 URL 都对应生产部署。如果希望先审查，应明确要求“保存但不要部署”。

因此推荐流程是：

```text
描述需求
  ↓
生成并保存
  ↓
人工检查内容、交互和数据
  ↓
修订
  ↓
确认访问权限
  ↓
明确批准部署
  ↓
分享链接并持续维护
```

不要把“创建一个 Site”与“立即公开发布”写成同一个模糊动作。

## 与 Codex 的协作

Sites 和 Codex 的最佳分工是：

| 环节 | 推荐工具 |
| --- | --- |
| 定义受众、数据和业务流程 | Chat / Work |
| 创建托管 Site | Work + Sites |
| 修改本地源码、运行测试 | Codex |
| 审查 Git Diff 和数据库迁移 | Codex Review |
| 保存但不发布的版本检查 | Sites 预览/保存流程 |
| 最终托管和分享 | Sites |

从本地项目创建 Site 时，还应在 Codex Review 中检查源码变更和可能的数据库迁移。关联信息可能保存在项目的 `.openai/hosting.json` 中；该文件属于项目配置，不应手工伪造未知的托管标识。

## Sites 与 Vercel 等外部托管的区别

| 维度 | Sites | 外部托管平台 |
| --- | --- | --- |
| 上手成本 | ChatGPT 内直接创建和管理 | 通常需要账号、项目和部署配置 |
| 控制粒度 | 托管流程更集成 | 基础设施和发布控制通常更完整 |
| 适用重点 | 快速内部工具、轻量应用、共享成果 | 专业产品、复杂环境和成熟 CI/CD |
| 预览与生产 | 部署 URL 即生产，需先保存审查 | 通常支持明确的 Preview/Production 环境 |

如果目标是快速交付内部工具，优先评估 Sites；如果需要完整工程控制、独立预览环境或既有云体系，则使用 Codex 配合 Vercel、Cloudflare 等托管插件更合适。

## 安全检查

- 发布前确认谁可以访问。
- 不把密钥写进前端代码或提交到仓库。
- 对表单、上传、数据库和身份验证进行真实测试。
- 检查是否泄露附件、Project 内容或内部系统字段。
- 生产部署前人工批准。
- 删除或停用 Site 前确认数据保留与依赖关系。

## 商业价值

Sites 是从“内容”走向“可交互产品”的低门槛路径。对于本项目，它可以用于：

- AI 工具选择器。
- 工作流模板目录。
- Codex 学习路线和进度看板。
- Prompt、Skill 与案例检索器。
- 面向潜在客户的流程诊断问卷。

但应先通过静态文档验证需求，再把访问频繁、需要交互的内容产品化为 Site。
